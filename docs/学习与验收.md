# 第一阶段学习与验收记录

验收日期：2026-08-30。本项目数据全部为模拟，不代表真实客户或经营成果。

## 你需要理解的三个关键知识点

### 1. 业务指标先规定时间和状态，再写求和

销售额来自有效支付明细；退款来自成功退款流水。这是两种不同业务事件。8 月 20 日支付 100 元、8 月 25 日退款 100 元，前一周仍有 100 元销售，本周计 100 元退款；不能改写原销售，也不能把原订单销售排除后再扣一次退款。

代码入口：`backend/metrics.py` 的 `aggregate()`。订单与退款分两次读取是有意设计：一个明细可对应多条退款，如果直接 JOIN 后 SUM 订单金额，会重复计算销售和成本。退款通过原明细关联商品，但按自身成功日期筛选。

可以自己验证：运行 `test_many_refunds_do_not_duplicate_sales_or_cost` 和 `test_cross_period_refund_does_not_rewrite_sales`；读测试中人为写入的 100 分订单和两笔退款，先用纸笔算答案。

### 2. 精确金额和“未知”是两种独立的数据问题

金额用整数分计算：例如销售 101 分，3 件商品每件成本 17 分，退款 19 分，贡献利润就是 `101 - 3 × 17 - 19 = 31` 分。只有前端格式化为元，不用浮点数累计经营金额。

成本 0 表示已确认免费，NULL 表示不知道。`finalize()` 遇到成本缺失时保留已知成本小计，但总成本、贡献利润返回 null。日趋势在缺失处断开，不能把缺口连成一个有依据的趋势。`change()` 使用 Decimal 计算百分比：前期零值返回原因，而不是除零；负基数采用绝对值，界面明确注明。

可以自己验证：`test_integer_cents_and_quantity`、`test_confirmed_zero_cost_is_valid`、`test_missing_cost_is_not_zero_and_only_affects_scope`、`test_change_zero_missing_negative_and_rounding`。注意本期采用支付日确认采购成本、退款不冲回的简化口径；商品贡献利润不叫净利润。

### 3. 测试要独立证明业务规则，而不是相信漂亮页面

核心测试直接构造小数据并写出预期值，不调用另一个相同公式当标准答案。API 测试验证错误参数、只读连接和范围限制。生成器测试在两个临时数据库生成同一批数据，比较完整 SQL 导出，并验证已有文件没有被覆盖。测试不修改演示数据库。

看板链路是 `表单筛选 → Flask 参数校验 → SQLite 只读数据 → metrics.py → JSON → React 展示`。`frontend/src/types.ts` 说明哪些字段可能为空；`Trend.tsx` 只负责坐标与显示。后续 AI 也必须沿预定义只读工具调用这条链路，不能自行猜金额、执行任意 SQL 或听从上传文字里的指令。

## 诚实的求职展示说法

可以说：「我使用 AI 辅助开发了一个基于模拟数据的电商经营复盘个人项目。我负责梳理指标口径、设计数据模型、验证核心计算，并实现本地看板。项目目前尚未接入真实店铺或模型。」

不要说「服务过客户」「帮助商家增加利润」「实现实际降本增效」或把模拟销售额说成个人/项目收入。展示亮点是业务边界清楚、缺失数据处理诚实、关键逻辑可测试，不是包装未经验证的效果。

第一阶段交付到此，等待验收，不自动推进后续功能。
