# 第二步：订单、退款与商品成本 Excel / CSV 导入

本模块处理单店铺、人民币、最长 90 天的交易观察期。不是平台 API，也不接模型。新增交易导入库与原来的模拟店铺、公开财报库分别存储。用户上传内容标记为「来源未核验」，不能据此宣称真实客户或经营成果。

## 启动和操作

本机依赖已安装、前端已构建。运行 `start.cmd`，打开 `http://127.0.0.1:5000/imports`，或点首页侧栏「交易表导入」。如果服务是旧版本，先在其终端 Ctrl+C，再启动。

从旧版升级或在新电脑运行，先执行 `setup.cmd`；新增 `openpyxl` 用于正确读取 Excel 类型/日期，`defusedxml` 用于拒绝危险 XML。依赖只安装在项目 `.venv`，不用全局安装。

1. 选择订单明细、退款明细或商品成本。
2. 首次指定完整观察期（含首尾，1～90 天），第一个文件成功导入后锁定。必须确保这段期间数据完整，系统无法判断用户漏传的订单/退款。不把文件日期的最小值/最大值擅自认定为完整观察期。
3. 上传单个 `.xlsx` 或 `.csv`，点「校验并预览」。预览仅用内存数据库，不写正式库。
4. 有错误：按原始行号与字段修复，重新选择文件和预览；整份文件不入库。有警告：明确查看缺失成本或空白行，再决定是否确认。相同重复行会完整列出。
5. 点「确认导入」或「接受警告并确认导入」。服务端持有写锁重新校验，所有有效新增/成本补齐一次性提交；失败则回滚，不能导入半份数据。
6. 点击「导入数据看板」查看真实后端计算。该看板仅统计交易导入库，旧模拟看板与财报入口仍独立可用。

退款依赖原订单，必须先导订单。成本可以先导，也可在订单后补充。上传顺序建议：成本 → 订单 → 退款；为了验收未知成本，也可先订单 → 退款 → 成本。

## 文件格式

首行必须是表头；中英文名称均支持，列顺序不限。**只支持下面的明确数据协议，不声称能自动识别所有电商平台导出文件。** 多余列请先移除，字段请按模板重命名；额外列、缺失列和别名重复都明确报错，不静默忽略。

|类型|中文表头|对应英文表头|
|---|---|---|
|订单|订单明细ID、订单号、商品编码、商品名称、支付日期、订单状态、数量、实付金额|order_line_id, order_id, product_id, product_name, paid_date, status, quantity, paid_amount|
|退款|退款流水ID、订单明细ID、退款日期、退款状态、退款金额|refund_id, order_line_id, refund_date, status, amount|
|成本|商品编码、成本生效日期、单位成本|product_id, effective_from, unit_cost|

- **订单明细 ID 不是订单号**。同订单可有多条商品明细，应提供稳定的明细 ID。不可用「文件行号」临时造 ID，否则换排序后无法可靠去重；源表没有 ID 时先在来源侧明确生成并长期保留。
- Excel 编号列必须设为文本，避免前导零和超过 15 位数字被 Excel 改写。系统拒绝数字型编号，不尝试恢复已经丢失的精度。商品名称也是文本。同编码不同名称会拒绝，避免不明来源的数据相互覆盖。
- 订单状态：`paid / shipped / completed / refunded / pending / cancelled`，或「已支付 / 已发货 / 已完成 / 已退款 / 待支付 / 已取消」。有效订单要求支付日期；待支付/取消要求支付日期为空、实付金额为 0。数量为正整数。
- 退款状态：`success / processing / failed`，或「成功 / 处理中 / 失败」。只有成功退款计指标；退款必须关联已支付明细，不能早于支付，成功累计不能超过实付金额。
- 日期：`YYYY-MM-DD`、`YYYY/MM/DD`、上述日期附 `HH:mm:ss`，或 Excel 日期单元格。按上海当地业务日处理，不接受时区猜测或模糊的 `08/09/2026`。CSV 数字序列日期无格式信息，直接拒绝。日期必须真实存在。成本生效日可早于观察期，但不能晚于结束日。
- 金额：人民币元，最多两位小数；不含千分位/货币符号/科学计数。入库转换为整数分，不四舍五入悄悄吞掉分以下精度。单行金额不超过一亿元。
- 成本列必须存在，但单元格可留空，表示未知。`0` 表示已经确认的零成本，不是未知。成本是单位采购成本，不是整行成本；系统按数量乘算。
- Excel 单工作表可任意命名；多工作表必须包含所选类型对应的「订单明细」「退款明细」或「商品成本」。其他工作表不导入，并在警告中列明。每次只处理一类。
- CSV 支持 UTF-8（含 BOM）和 GB18030；每次上限 5 MB、5000 数据行（包含空白行），Excel 上限 30 列。旧版 `.xls`、加密工作簿、宏、外部链接、公式和错误单元格不接受。请将公式结果粘贴为值后上传。

## 重复、冲突与成本补齐

|情况|处理|
|---|---|
|同一文件重复导入、改名后导入、相同数据换 CSV/XLSX|按规范化业务主键和字段内容识别，新增 0，不重复计数；不会再新增导入历史批次|
|同文件里同一明细重复出现|第一条候选新增，后续相同内容明确列为重复；不按订单号去重|
|同主键不同金额、商品、日期或状态|冲突错误，指出当前行及原批次/行；整份回滚，禁止静默覆盖。当前版本不支持订单状态自动更新|
|订单支付日找不到成本版本|订单可带警告导入，成本快照为 NULL；该范围的总成本和商品贡献利润为 null，展示不可计算|
|成本版本已有未知值，后续同版本填入金额|允许明确补齐；重复输入相同值不重复更新|
|后续新成本能补齐旧订单未知快照|按支付日适用的最新成本版本回填，只补 NULL；显示补齐订单数|
|新版本会改变旧订单已知成本|拒绝并指出成本文件行和受影响订单 ID；不自动重写历史|
|空白行|展示警告和原始行号后跳过，不把空白算成有效交易|
|任一错误|整份文件不导入；界面分页展示全部错误，JSON 报告完整下载，无前 100 条截断|

预览与确认间可能有其他提交，所以确认时重新检查。发生断线、无法确定提交结果时，重新预览同一文件即可：若已成功，会明确显示重复。查询使用只读连接，并在一次读取事务内计算，避免一半旧数据、一半新数据。

## 数据库与代码

`data/imported_transactions.sqlite3`：首次有效确认时创建。复用 products / product_costs / order_lines / refunds 的金额约束与关系结构；固定 `is_simulated=0` 在这里仅表示不是原生成器数据，**不表示已核实真实性**。dataset_meta.label 和 API source 明确标为 `user_upload_unverified`。原 `data/demo.sqlite3` 不迁移、不修改；公开财报库也不修改。

新增追溯表：

|表|字段|含义|
|---|---|---|
|import_batches|id, kind, filename, sha256, imported_at, report|每个有效写入批次；SHA256 为原文件摘要；时间 UTC；报告 JSON；无效文件报告不落库|
|import_rows|kind + business_key（联合主键）, payload, batch_id, source_row|规范化行内容与当前来源批次/原始物理行号；成本补齐后来源更新为补齐文件|

原始附件不长期保存；规范化业务数据和追溯记录留在本机 SQLite。导入数据库已由 `.gitignore` 排除。真实数据不要提交仓库。错误报告也可能含商品编号，分享前检查。

- `transaction_files.py`：读取表格 → 检查表头 → 保留原始行号 → 转为规范化字段。金额 Decimal 转整数分，不执行单元格文本。
- `transaction_store.py`：业务键判断、内存试算、退款关联、成本回填、追溯。
- `transaction_imports.py`：本地预览/提交接口、模板下载、导入库只读看板。
- `frontend/src/TransactionImports.tsx`：文件选择、预览、逐行反馈、确认与历史。
- `frontend/src/main.tsx`：原看板复用，按页面入口切换独立 API，不把统计值写在前端。

API：`GET /api/imports/meta`，`GET /api/imports/dashboard`，`POST /api/imports/preview`，`POST /api/imports/commit`。POST 为 multipart 的 `file, kind, start, end`，并要求同源自定义头 `X-Import-Request: commerce-insight`，不开放 CORS；SQL 使用绑定参数。返回 422 表示逐行错误，400 表示文件或参数错误，403 表示来源保护拒绝，413 表示超限。

## 可复现验收步骤

导入页展开「下载模拟测试文件」，所有示例都以 SIM 开头，与吉宏或其他公司的公开财报无关。使用观察期 2026-08-01～08-30。

1. 上传错误订单示例：应显示第 2 行错误日期，第 3 行缺订单号及金额精度错误，确认按钮不可用，库内新增 0。
2. 上传订单示例：预览待新增 2 行、2 条缺失成本警告；确认后销售 157 元，成本/利润不可计算。
3. 再次预览并确认同一订单文件：2 条重复，新增 0，销售仍为 157 元。
4. 导入退款示例：退款 29.50 元，利润仍不可计算。重复导入退款不会再扣一次。
5. 导入成本缺失示例：只知道随行杯每件成本 24 元；收纳盒成本仍未知，整体利润不能当零成本计算。
6. 导入补齐成本示例：收纳盒每件成本 16 元。成本合计 64 元，贡献利润 `157 − 29.50 − 64 = 63.50` 元。看板选择 08-24～08-30。
7. 公司 `annual_data.csv` 传到订单入口：表头错误；原公司财报请走 `/public-financials`，不能把年度收入人为拆成订单。

自动化命令：`.\.venv\Scripts\python.exe -m unittest discover -s backend\tests -v`；前端在 frontend 运行 `npm.cmd run build`。测试使用内存/临时数据库，并核对原模拟库哈希不变。

## 需要理解的三个知识点

1. **幂等性靠业务键，而不是文件名**：同样的业务事实换文件、换排序、换格式后，仍不能重复计算。哈希用于追溯，不作为唯一去重依据。
2. **校验与事务配合**：先给出完整反馈，确认时再校验；有错误整份回滚。UI 的“通过”不能代替服务端检查，尤其是并发和断线重试。
3. **未知数据要保留未知**：缺失成本不是零，只有补齐适用成本后才能计算利润；这比输出一个好看的错误利润更重要。

边界：不支持多店铺混合、自动映射任意平台字段、历史已知数据改写、超 90 天观察期扩展；不接 AI，不导出经营周报。当前下载的是校验报告，不是周报。
